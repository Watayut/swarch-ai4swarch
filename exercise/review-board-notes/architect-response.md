# คำตอบของสถาปนิก (ผู้เขียน ADR-0002) ในช่วง open discussion

ภาพรวม: ทุกคนเห็นตรงกันว่าทิศทางหลักถูก (ส่ง event แบบ asynchronous ผ่าน RabbitMQ แต่ละงานมีคิวของตัวเอง) แต่ ADR เขียน "ตอนที่ทุกอย่างปกติ" ละเอียด และเขียน "ตอนที่พัง" หยาบ

## สิ่งที่ยอมรับและจะแก้ 2 เรื่องหลัก

### 1. ส่วน "เมื่อพัง" ต้องทำงานเองโดยไม่พึ่งคน
- **ถอน "ยิงซ้ำด้วยมือ" ออก** (ตอบ AI Risk 1–2, SRE A5, PO A2) เปลี่ยนเป็น: ถ้าส่งเข้า broker ไม่ได้ภายใน 50 ms ให้เก็บ event ไว้ใน spool แล้วมี worker ส่งซ้ำเองโดยไม่ให้แต้มซ้ำ และ checkout ต้อง start ได้แม้ broker ล่ม
- **แต้มได้ครั้งเดียวจริง** (ตอบ AI Risk 4, PO A2): `loyaltyservice` ใช้ PostgreSQL บันทึก "ทำ order นี้แล้ว" กับยอดแต้มในครั้งเดียวกัน และเอา TTL ออกจากคิวแต้ม
- **ยอมรับว่า prefetch คุม 50 emails/s ไม่ได้** (AI Risk 3) เป็นความผิดพลาดทางเทคนิคของผมเอง แก้เป็น token bucket 50/s

### 2. ทำทั้งหมดไม่ทันใน 15 วัน จึงแบ่งเฟส
- **ปีนี้:** RabbitMQ 1 node + spool, `emailservice` ส่ง MailFast ไม่เกิน 50/s, `loyaltyservice` แบบได้ครั้งเดียว, หน้ายืนยันโชว์ "คุณจะได้รับ X แต้ม" (ตอบ PO A1, A3 และ SRE A2, A4)
- **เลื่อนหลัง 11.11:** analytics consumer, 3-node cluster, event คืนเงิน/หักแต้ม, fraud scoring (ตอบ PO A4–A5)
- **ก่อนขึ้น production:** checklist ของ SRE, ระบุชื่อคนเวร, load test 4 และ 7 พ.ย., game day 6 พ.ย. (ตอบ SRE A1–A3) แผนสำรองถ้าไม่ผ่าน: ปิด feature flag กลับไปใช้ทางเดิม แปลว่า MailFast และแต้มอัตโนมัติไม่ทันปีนี้ ซึ่ง PO เป็นคนตัดสิน

|---|---|---|

## สิ่งที่แปลกใจที่สุด
SRE A3 เรื่อง silent failure: จุดที่ผมภูมิใจที่สุด ("checkout สำเร็จเสมอ") คือจุดเดียวกับที่ทำให้ไม่มีใครรู้เมื่ออีเมลและแต้มหยุดออก และความยาวคิวที่ผมเสนอเป็น signal หลักใช้ไม่ได้โดยธรรมชาติในช่วง peak
