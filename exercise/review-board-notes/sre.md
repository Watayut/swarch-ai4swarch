# ความเห็นของ SRE (อ่านการ์ด S)

มุมมอง: ผมคือคนที่จะโดนปลุกตอนตีสามถ้าของชิ้นนี้พัง เห็นด้วยกับทิศทางหลัก แต่ ADR เขียนเหมือน RabbitMQ แค่ deploy ก็จบ

## ประเด็นหลัก 2 ข้อ

### A3. ถ้าอีเมลหยุดส่ง จะไม่มีใครรู้
- **พูดง่าย ๆ:** 11.11 ปีที่แล้วผู้ให้บริการอีเมลล่ม 20 นาที ไม่มีใครรู้จนลูกค้าบ่นในโซเชียล ADR นี้ทำให้มองเห็นยากกว่าเดิม เพราะ checkout "สำเร็จเสมอ" โดยตั้งใจ และคิวอีเมลจะยาวขึ้นเป็นปกติช่วง peak อยู่แล้ว alert ที่ดูแค่ความยาวคิวจะดังทั้งวันจนโดนปิด
- **อยากให้แก้:** alert จาก "ข้อความเก่าสุดในคิวค้างนานแค่ไหน" และ "consumer ยังทำงานอยู่ไหม" แทนความยาวคิว ใส่ `order_id` ไว้ตามรอยได้ทั้งเส้นทาง และยิงออเดอร์ทดสอบทุก 5 นาที
- **AI เห็นไหม:** ไม่ เรื่องปีที่แล้วรู้ไม่ได้ แต่ "คิวยาวช่วง peak เป็นเรื่องปกติ จึงใช้เป็น alert ไม่ได้" ควรอนุมานได้จากตัวเลข 200/s กับ 50/s

### A5. "ยิงซ้ำด้วยมือ" = โยนงาน 12,000 ชิ้นให้คนเวร 2 คนตอนตีสาม
- **พูดง่าย ๆ:** broker หายแค่ 1 นาทีช่วง peak = 12,000 event ที่คนเวรต้องนั่งยิงซ้ำในคืน 11.11 แถมเอาอีเมลและที่อยู่ลูกค้าไปไว้ใน log และเครื่องมือยิงซ้ำยังไม่มีใครเขียน
- **อยากให้แก้:** ให้ระบบเก็บ event ที่ส่งไม่ได้ไว้เอง (spool) แล้วส่งซ้ำอัตโนมัติ ไม่ต้องใช้คน และห้าม checkout รอ broker นานเกินหลักสิบ ms
- **AI เห็นไหม:** เห็นเกือบทั้งหมด สิ่งที่ SRE เพิ่มคือมุมภาระของคนเวร

## ประเด็นอื่นที่ยกสั้น ๆ
- **A1** "ทีมมีประสบการณ์ RabbitMQ" จริง ๆ คือเคยรันบนโน้ตบุ๊ก ไม่มีใครเคยดูแลบน production และเวรมีแค่ 2 คน ADR ต้องระบุว่าใครเป็นเจ้าของและใครโดนเรียก
- **A2** ของใหม่ที่เก็บ state ต้องมี dashboard, alert, backup, runbook ก่อนขึ้น production ใช้เวลาราว 1 สัปดาห์ที่ ADR ไม่ได้จองไว้
- **A4** cluster ใกล้เต็ม node การขอ 3 node ใหม่ต้องรองบ 2 สัปดาห์ เหลือ 15 วัน ไม่ทัน ควรเริ่มที่ 1 node + spool ก่อน

## ผลโหวต
**อนุมัติโดยมีเงื่อนไข** จะยอมให้ขึ้น production เมื่อ ADR เพิ่ม (1) checklist ก่อนขึ้น production พร้อมชื่อคนเวร (2) ส่งซ้ำอัตโนมัติแทนทำด้วยมือ (3) แผนที่ยอมรับว่า 3 node ไม่ทัน 11.11 ปีนี้
